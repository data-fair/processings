# Data Fair Processings — Agent Guidelines

## Project Overview

`@data-fair/processings` is a sister service of `data-fair`. It runs scheduled and on-demand
processings (NPM-installable plugins) that ingest, transform and publish datasets into a
running `data-fair` instance. The project is a monorepo with four workspaces:

- `api/` — Express REST API
- `worker/` — Polling worker that runs the processings tasks in child processes
- `ui/` — Vue 3 + Vuetify SPA (built with Vite)
- `shared/` — TypeScript types and helpers shared between api, worker and ui

## Dev environment

The user starts the dev environment of a checkout with `npm run dev-zellij` (zellij >= 0.44, session named after the checkout directory). Agents never start or kill the session, and act on processes and containers only through `df-dev`:

```bash
npx --no df-dev status                # containers (health, memory), panes (running / exited + code, readiness), dev processes memory
npx --no df-dev logs api -n 100       # last lines of a pane: api, worker, ui
npx --no df-dev restart worker        # Ctrl+C, rerun, wait for its readiness URL
npx --no df-dev up events             # optional container (compose profile), then restart api and worker
```

- Read the logs before restarting: nodemon (api, worker) and vite (ui) already reload on file changes. Restart only a pane that exited, hangs, or needs new env.
- If `restart` answers "not ready", report to the user with the logs instead of retrying.
- Never use `docker compose restart`, `kill` or `zellij action` directly, nor `npm ci` / `npm install` while the env runs.
- Always `npx --no df-dev`: without `--no`, npx would download an unrelated public package if the dependency were missing.
- Optional containers: `events` (notifications; when absent the api and worker run with `privateEventsUrl: ""`), `openapi-viewer` (API docs) and `maildev` (catches the mails of simple-directory and of the worker's transport, plugins' `sendMail`). The user can start them with the env: `npm run dev-zellij -- --services events,openapi-viewer`.

The dev environment also serves as the test environment: the Playwright test suite hits the
running dev API, dev worker and dev UI. There is no separate test server.

Each git worktree gets its own `.env` (random ports + `<branch>.localhost` subdomain) so
multiple worktrees coexist without port collisions. From the main checkout:

```bash
npx --no df-worktree feat-xyz          # ../processings_feat-xyz: npm ci + df-dev setup (.env, types, UI build)
npx --no df-worktree-delete feat-xyz   # containers, volumes, zellij session, then the worktree
```

Branch names: letters, digits, `.`, `_`, `-`, at most 60 characters, no `/`.

### Port assignments

Port numbers and the `DEV_HOST` subdomain live in `.env` (gitignored, generated by
`npx --no df-dev setup` from `dev/dev.json`). Do not modify port assignments by hand.

### Test users

Test fixtures live in `dev/resources/users.json` and `dev/resources/organizations.json`.
All test users and orgs are prefixed with `test_` (e.g. `test_admin1@test.com`,
`test_org1`). The cleanup endpoint `DELETE /api/v1/test-env` only purges documents
whose `owner.id` matches `^test_` so that interactive dev work under non-prefixed
accounts (e.g. `superadmin`, `albanm`) survives test runs.

Special accounts:
- `test_superadmin@test.com` / password `superpasswd` — superadmin
- all other `test_*@test.com` — password `passwd`

### Test-env API

When `NODE_ENV=development` the API exposes `/api/v1/test-env`:
- `DELETE /` — delete all `test_*`-owned processings, runs and limits
- `GET /pending-tasks` — list runs in `triggered`/`scheduled`/`running` status
- `GET /raw-processing/:id`, `GET /raw-run/:id` — raw mongo docs
- `POST /set-env`, `POST /set-config` — runtime overrides for testing
- `DELETE /plugins` — wipe the installed plugins directory

These endpoints are used by the Playwright support helpers in `tests/support/axios.ts`.

### Testing

```bash
npm test                          # all tests (no --max-failures: one flake must not hide the rest)
npm run test-unit                 # unit tests only
npm run test-api                  # API tests only
npm run test-api-fast             # API tests, stop at the first failure (iteration)
npm run test-e2e                  # e2e tests only
npx playwright test path/to/file  # specific file
```

The run writes per-test durations to `dev/logs/test-timings.json`, and keeps a trace and a
screenshot of each failing test in `test-results/` (`npx playwright show-trace <zip>`).
Timeout: 30 s per test, hooks included; specs that run plugins through the worker call
`test.slow()` instead of raising it. `clean()` fails, naming the runs, when the worker is
still busy after 10 s: the culprit is the test that left them.

e2e specs log in through the simple-directory API (`tests/fixtures/login.ts`, one login per
user and worker, renewed after 10 min) and turn off lib-vue's keepalive with a future
`sd-keepalive` localStorage timestamp, so no page ever rotates the shared exchange token.

Tests are organized under `tests/features/<topic>/<name>.{unit,api,e2e}.spec.ts`.
The `state-setup` project pings `/api/v1/test-env/pending-tasks` and seeds the data-fair API
key of the worker. Pure logic goes to unit specs; api specs cover the HTTP contract and the
worker; e2e specs only cover user flows and what only a browser can check.

The `e2e` project depends on `e2e-warmup` (`tests/e2e-warmup.ts`), which walks the list
and edit routes once before the specs run, so a cold Vite transforms them first. Dependency
discovery is off: a blank page there with a module named in the console means a commonjs
dependency is missing from `optimizeDeps.include` in `ui/vite.config.ts` (use the exact import
specifier). Running an e2e spec alone still goes through the warmup.

When iterating on changes always run only the related test cases.

Quality gates:

| When | Where | What |
|---|---|---|
| commit | `.husky/pre-commit` | `npm run lint` |
| push | `.husky/pre-push` → `dev/pre-push.sh` | type check, all unit tests, the `@smoke` api/e2e set, and the api/e2e spec files changed since `origin/master` |
| pull request | `pull-requests.yml` → `reuse-quality.yml` | lint, builds, type check, audit, then the whole unit/api/e2e suite (1 retry) |
| release tag | `releases.yml` → `reuse-quality.yml` | the same, before building the images |

`npm run quality` still runs the whole gate locally. A test joins the `@smoke` set
(`test('...', { tag: '@smoke' }, ...)`) only if it is fast and covers a core flow (create,
permissions, run, edit form); check its duration in `dev/logs/test-timings.json`.
